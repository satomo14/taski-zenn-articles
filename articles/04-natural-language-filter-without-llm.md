タスク管理ツールの絞り込み機能は、だいたい使われません。

担当者のプルダウンを開いて、ステータスのプルダウンを開いて、期限の日付を2つ入れて──という3ステップを毎回やるくらいなら、全件を目で見たほうが速いからです。高機能なカスタムクエリが用意されていても、**最初の1個を作る手間が発生した時点で使われなくなる**、というのは Redmine を長く使っているチームでもよく見る光景でした。

そこで、コマンドパレット（`Ctrl+K`）に **「田中さん担当で今週期限の未完了タスク」と打つだけで絞り込める**ようにしました。この記事は、それを **LLM を一切呼ばずに**実装した話です。

## なぜ LLM を使わなかったのか

自然文の解釈と聞くと真っ先に LLM が浮かびますし、実際このアプリには Gemini を使った機能が別にあります。それでもこの機能では使いませんでした。理由は2つです。

**1つ目は、AI が全員に効く前提ではないから。** このアプリの AI 機能は BYO-key 方式で、利用者が自分の Gemini API キーを設定して初めて動きます（自社の API 原価をゼロにするための設計で、これは[別記事](https://zenn.dev/taski_app/articles/02-byok-ai-free-plan-devlog)に書きました）。つまり **LLM に依存させると、キーを入れていない人には存在しない機能になります。** 絞り込みは全員が毎日触る導線なので、ここを条件付きにはできません。

**2つ目は、レイテンシが体験を壊すから。** 検索窓は1文字打つたびに結果が変わるものです。ここに数百ミリ秒の往復が挟まると、「打ち終わってから待つ」道具に変わってしまいます。ルールベースなら同期的に返せるので、**入力中にリアルタイムで解釈結果を出せます。**

要件を絞って考えると、扱う語彙は「担当者・優先度・タグ・ステータス・期限・放置日数・並び順」だけです。**閉じた語彙を閉じた条件に写すだけなら、正規表現とキーワードの辞書で十分に届きます。**

## 設計: 「消費」と「残余」

素直に書くと、条件ごとに `if (query.includes('今週'))` を並べることになります。これだけだと1つ問題が残ります。**条件として使われなかった部分をキーワード検索に回したい**、という要求です。

「ログイン画面のバグで今週期限のもの」と打たれたら、`今週期限` は日付範囲に、`ログイン画面` はフリーワード検索に振り分けたい。でも素朴な実装だと、条件を読み取ったあとの文字列がそのまま残っていて、`今週期限のログイン画面のバグ` 全体でキーワード検索してしまい、当然0件になります。

そこで、**解釈に使った語句を `consumed` に積んでいき、最後に元の文字列から引き算する**方式にしました。

```ts
const consumed: string[] = [];      // 条件として消費した語句
const summaryParts: string[] = [];  // 画面に出す解釈結果のバッジ

// --- 担当者 ---
if (includesAny(query, SELF_WORDS) && ctx.currentUserId) {
  const hit = SELF_WORDS.find((w) => query.includes(w))!;
  filters.showMyTasksOnly = true;
  summaryParts.push('👤 自分が担当');
  consumed.push(hit);
  hasSignal = true;
}
// … 優先度・タグ・ステータス・期限・放置日数も同じ形で consumed に積む
```

最後に引き算して、残ったものをキーワードにします。

```ts
let leftover = query;
[...consumed, ...GENERIC_NOISE_WORDS]
  .sort((a, b) => b.length - a.length)   // ← 長い語句から消す
  .forEach((phrase) => {
    if (phrase) leftover = leftover.split(phrase).join('');
  });
leftover = leftover
  .replace(/\d+/g, '')
  .replace(/[のはがをにでとからまでもう、。・\s]/g, '')
  .trim();

if (leftover.length >= 2) {
  filters.searchTerm = leftover;
  summaryParts.push(`🔍 "${leftover}"`);
}
```

`GENERIC_NOISE_WORDS` は「タスク」「一覧」「表示して」「ください」のような、条件でもキーワードでもない語の辞書です。これを引いておかないと、`ログイン画面のバグを表示して` の「表示して」がキーワードに混ざります。

### 長い語句から消す、が地味に効く

上のコードで一番ハマったのが `.sort((a, b) => b.length - a.length)` です。

`今週` と `今週中` の両方が辞書にあるとき、**短いほうから消すと `今週中` が `中` になって残ります。** そして `中` は1文字なので `leftover.length >= 2` の条件をすり抜けたり、逆に別の語とくっついて意味不明なキーワードになったりします。

日本語は語句が入れ子になりやすいので、**辞書から文字列を引き算する処理は必ず長い順**にする必要がありました。同じ理由で `norm()` として `String.prototype.normalize('NFKC')` も先に通しています。全角で `３日以内` と打たれても `3日以内` として拾うためです。

## 曖昧なときは「解釈しない」を選ぶ

推測する機能で一番まずいのは、**間違った推測を黙って適用すること**です。絞り込みの場合、条件を1つ取り違えると「0件です」とだけ表示され、利用者にはツールが壊れたようにしか見えません。

なので、一意に決められない場面では**その条件だけを落とす**ようにしました。

**ケース1: 完了ステータスが複数あるとき。** このアプリのステータスはプロジェクトごとに自由に定義でき、「完了」フラグの立ったステータスが複数あり得ます（「完了」と「却下」の両方など）。「完了したタスク」と言われても、どれを指すのか決められません。

```ts
const closedStatuses = ctx.statuses.filter((s) => s.is_closed);
if (closedStatuses.length === 1) {
  filters.statusFilter = closedStatuses[0].key;
  summaryParts.push(`🟢 ${closedStatuses[0].label}`);
} else {
  // 完了扱いのステータスが複数あり一意に決められないため、ステータス条件は反映しない
  summaryParts.push('🟢 完了（複数ステータスのため未反映）');
}
```

適当に先頭を選ぶこともできましたが、**「未反映」と画面に書いて出す**ほうを選びました。黙って外すと、利用者は却下ぶんが消えた一覧を完了一覧だと思って読んでしまいます。

**ケース2: 姓だけで書かれたとき。** 「田中さん担当で」の「田中」は、チームに田中さんが2人いたら決められません。フルネーム一致 → スペース詰めの一致 → 姓の一致、の順で試して、**姓で一致した候補が複数いる場合は担当者条件そのものを付けません。**

```ts
const candidates = ctx.members.filter((m) => {
  const family = familyNameOf(m.full_name || '');
  return family.length >= 2 && query.includes(family);
});
const uniqueFamilies = new Set(candidates.map((m) => familyNameOf(m.full_name)));
if (candidates.length > 0 && uniqueFamilies.size === 1) {
  member = candidates[0];
  matchedNameSubstring = familyNameOf(member.full_name);
}
```

## 何も読み取れなかったときは、候補を出さない

コマンドパレットは通常のキーワード検索も兼ねています。ここで「スマートフィルターとして絞り込む」という候補を常に出すと、`ログイン` と打っただけの人にも意味のない選択肢が並びます。

そこで、**条件を1つでも読み取れたか**を `hasSignal` として返し、コマンドパレット側の表示条件にしました。

```ts
const smartFilterResult =
  query.trim().length >= 2 && onApplySmartFilter
    ? parseSmartFilterQuery(query, { members: allMembers, teams, tags, statuses, currentUserId: currentUser?.id })
    : null;

const smartFilterActions = smartFilterResult?.hasSignal
  ? [{
      title: `“${query.trim()}” で絞り込む — ${smartFilterResult.summaryParts.join(' / ')}`,
      action: () => onApplySmartFilter!(query.trim(), smartFilterResult),
    }]
  : [];
```

`summaryParts` をそのまま候補のラベルに出しているのがポイントです。**押す前に「👤 田中太郎 / 📅 期限: 今週 / 🔵 未完了」と見えている**ので、解釈がずれていればその場で分かります。適用後も一覧の上にバナーとして出しっぱなしにしています。

推測する機能を信用してもらうには、**推測の中身を常に見せておくのが一番安上がり**でした。LLM を使わなかったことで解釈が決定的になり、「なぜこう解釈されたか」を説明できるのは副次的な利点です。

## 期限だけでなく「放置日数」を入れた

実際に運用してみて、期限より使われたのがこちらでした。

```
先週から動いていないバグ
2週間更新がないタスク
```

`動いていない` `更新がない` `放置` `停滞` といった語をトリガーに、`notUpdatedSinceDays` へ変換します。`先週` なら先週の開始日から今日までの日数を計算し、`2週間` なら14、数字がなければ既定で7日です。

朝会前に放置チケットを拾う用途にはまるので、**期限（未来向き）と放置（過去向き）はセットで用意する価値があります。** 期限のUIしか無いツールが多いのですが、実運用で困るのはむしろ後者でした。

## 限界: 数字が2つ出てくる文はまだ正しく取れない

正直に書いておくと、既知の穴があります。

```
期限が3日以内で、7日以上動いていないタスク
```

期限側は `/(\d+)\s*日\s*以内/` で `3日以内` を正しく拾いますが、放置側は `/(\d+)\s*日/` の**最左一致**なので、同じ `3` を拾って「3日以上更新なし」と解釈してしまいます。

直すなら、期限側で消費した部分文字列を放置側の走査対象から先に除外する（`consumed` を引き算してから次の条件を読む）のが素直です。ただ**この文型が実際に打たれたことは今のところ一度もない**ので、直さずに限界として認識しておく側に倒しています。ルールベースは穴を無限に見つけられるので、**実際に打たれた入力だけを直す**と決めないと際限がありません。

## まとめ

- **閉じた語彙・閉じた条件なら、自然文の解釈に LLM は要らない。** 正規表現と辞書で届く範囲は思ったより広い
- **同期的に返せることが最大の利点。** 検索窓は1文字ごとに結果が変わる場所なので、往復の待ちが入ると道具の性質が変わってしまう
- **辞書から文字列を引き算するときは長い語句から。** 日本語は語句が入れ子になる
- **一意に決められない条件は、適当に選ばず落とす。** そして落としたことを画面に書く
- **解釈結果は適用前から見せる。** 推測する機能は、推測の中身が見えて初めて信用される

「絞り込みが定着しない」の正体は機能不足ではなく、たいてい**最初の1回の手数**でした。そこだけを削る実装なら、これくらいの規模で足ります。
